# AI Instructions — Pillaro Dataverse Plugin Framework

This is the canonical entry point for any AI coding agent working in a solution built on the
Pillaro Dataverse Plugin Framework. Every other agent-config file (`CLAUDE.md`,
`.github/copilot-instructions.md`, `.cursor/rules/*`) is a thin redirect to this file — do not
duplicate rules there.

Rules below use stable IDs (`PF-XXX-NNN`). Reference the ID in commits, PR descriptions, and review
comments. Full rationale and source docs live in [`docs/ai/rules/`](./docs/ai/rules/); this file is
the index and the hard boundaries. Read the specific rule file for the area you are touching before
writing code there.

## 🛑 Hard boundaries — read first

These are not style preferences. Violating them causes silent production incidents or breaks other
developers' work. No task justifies skipping them.

1. **PF-ARCH-001/002** — business logic MUST live in `Logic`. `Plugins` is deployment shell only.
2. **PF-DATA-005/006/007** — NEVER write or edit files under `EarlyBound/`. They are generated by
   `pac modelbuilder` from `Logic`. A missing type or attribute means STOP and tell the developer
   what to generate — never hand-write a partial class or fall back to late-bound access to route
   around it.
3. **PF-REG-002/003** — NEVER invent a GUID for a step ID or image ID, and NEVER copy one from
   `/docs` or `/examples`. Colliding IDs across solutions corrupt registration metadata on deploy.
4. **PF-ERR-001** — an expected business rejection is `DataverseValidationException` (task ends
   `Success` + `Info` in the log), never `InvalidPluginExecutionException` (creates a false `Error`
   in monitoring for something that isn't one).
5. **PF-PROC-004/005** — NEVER commit a connection string, secret, or `key.snk` content. NEVER run
   `deploy` yourself. Deployment is a human action, run through the team's own pipeline.
6. **PF-ENV-*** (§7 below) — if you have a live dev Dataverse connection, you may run integration
   tests against it, under strict conditions. You may never run them against anything else.
7. **PF-TEST-001** — tests are integration tests against real Dataverse. NEVER mock
   `IOrganizationService` or Dataverse behavior to make a test pass.

If a rule below conflicts with something you see in `/docs` prose, the rule wins — some prose has
known gaps tracked in [`docs/ai/ai-readiness-fix-plan.md`](./docs/ai/ai-readiness-fix-plan.md).
If a rule conflicts with `/examples` code, stop and ask a human; `/examples` is meant to be the
canonical form and a conflict means one of the two has drifted.

## 🔁 Analysis → plugin → task workflow

This is the framework's main advantage: a 1:1 mapping between an analysis item and one task file. It
is also how this framework supports a delivery consultant who does not write C# — full method,
requirement-intake format, and worked examples: [`docs/ai/analysis-workflow.md`](./docs/ai/analysis-workflow.md).
Summary:

1. **Break the requirement into plugins first.** A plugin groups steps around one entity or one
   functional area (`ContactPlugin`, `AccountPlugin`). Name it before naming any task. **Look for an
   existing `<Entity>Plugin` first** — in a mature solution the usual change is a new task on an
   existing step, not a new plugin (PF-REG-010).
2. **Break each plugin into tasks.** One task = one business responsibility (PF-TASK-002). If a
   requirement has an "and" in it that isn't purely incidental, it is probably two tasks.
3. **For each task, write down before coding:** entity, message(s), stage, mode, the precondition(s)
   that make it fire, what it reads, what it writes, and the log lines it should emit. This is the
   task's contract — the validation chain and the tests both come directly from it.
4. **Present the plan (plugins + tasks + tests) for review before writing any code.** This is the
   cheap checkpoint — changing a plan is a text edit, changing code after the fact costs more.
5. **Tests before implementation.** Write the test(s) for the task's happy path and its business
   rejection path first, run them (red), then implement (green). See PF-TEST-005 and
   [`docs/ai/rules/70-testing.md`](./docs/ai/rules/70-testing.md).
6. **Verify with the fast loop before asking for review.** See
   [`docs/ai/verify.md`](./docs/ai/verify.md).

## ✅ Fast loop (run yourself, every change)

Exact commands: [`docs/ai/verify.md`](./docs/ai/verify.md). Summary:

```text
1. dotnet build "<Logic project>.csproj" -c Release      # zero warnings (PF-BUILD-001)
2. pillaro-dv manifest --assembly <built assembly> --output artifacts/plugin-manifest.json
3. pillaro-dv validate --manifest artifacts/plugin-manifest.json
```

Both CLI commands run offline — no Dataverse connection needed — and return a non-zero exit code on
failure. Treat a non-zero exit code as a hard stop, not a suggestion.

The fast loop cannot catch a merged `Plugins` DLL without `ProxyTypesAssemblyAttribute`
(PF-BUILD-006): it builds and validates cleanly, then every early-bound call fails inside Dataverse
with "not a known entity type" or "the deserializer has no knowledge of any type". If you see either
message, fix the assembly — never rewrite the task to late-bound.

## 🐢 Slow loop (integration tests — conditions apply)

Only if you have been given a live connection to a **dedicated dev environment** (never test/UAT/
production):

- `docs/ai/rules/70-testing.md` and the `PF-ENV-*` rules are mandatory reading before running any
  test that touches that connection.
- The test fixture verifies the connected environment against `ExpectedEnvironmentUrl`
  (`PF-ENV-006`) and throws if they don't match — never bypass or remove that check.
- A failing integration test is fixed by fixing the task, or escalated to a human. Never "fixed" by
  editing the test until it passes (`PF-ENV-007`).
